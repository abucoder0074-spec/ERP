# ADR 0001 · Shared login throttling

## Context

The first Phase 0 scaffold attempted to count requests in PostgreSQL before rendering a Django form. The requirement is to count failures only, limit both IP and case-insensitive username, and refuse an over-limit request before Django evaluates credentials. Web runs with multiple workers.

## Decision

Use Redis with expiring HMAC-keyed IP and NFKC/casefolded username counters. One atomic script checks both counters and acquires both short-lived leases. Another verifies lease ownership, records a failure or clears both counters after success, and releases the leases. Counters expire relative to the first failure. A 429 contains no form and uses the longest remaining blocking TTL for Retry-After. An overlapping request or cache outage receives a generic 503, so it can retry without authorizing an additional password check.

Use the immediate peer IP. An explicitly allowlisted proxy can supply an overwritten X-Real-IP header. Django's default password hasher runs for a nonexistent or unusable account, and the UI uses a common failure message. The throttle normalizes usernames independently of Django's case-sensitive username lookup.

## Consequences

Redis is required for sign-in. A valid login resets the shared IP counter, which can also clear failures made by another person behind the same NAT. Username limits apply independently across IPs. A hostile client can temporarily block a guessed username. Losing Redis data clears current lockouts, so Compose enables AOF. If a password check outlives its lease, its result cannot authorize a session. The prior DB table is removed by a reversible migration that preserves existing workspace permission assignments.
